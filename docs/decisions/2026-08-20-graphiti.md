# “Graphiti currency” has three meanings

1. **Currently works:** how the live path actually behaves;
2. **Temporal currency:** how Graphiti knows a fact is still valid, outdated, or later overturned;
3. **Monetary currency:** actual cost and how the £250 budget is debited.

---

# 1. What Graphiti is in this product

Graphiti should not be understood as:

> Extract a few entities for this draft, in case the next draft needs them.

A more accurate reading is:

> Graphiti is a **temporal proposal engine** that reads source episodes one by one, resolves entities across sources, extracts relationships, and identifies new, old and possibly contradictory facts.

In the Newsroom architecture it remains only:

```text
stochastic extractor / proposal producer
```

and not:

```text
editorial authority
```

True authority remains the relational ledger, retained permitted objects, admission decisions and the governed projector. The Graphiti private graph can be wiped; admitted entity and relation history MUST NOT depend on it existing. The existing GRAG specification already has this right: Graphiti is proposal-only, workspace-isolated, separately admitted, and graph projection is non-authoritative.

The intended flow is:

```text
SourceRevision / DiscoveryRepresentation
                  │
                  │ rights + access gate
                  ▼
        Graphiti corpus ingest queue
                  │
                  ▼
      untrusted proposal generation
      entities + relations + timestamps
                  │
                  ▼
        retain exact proposal receipts
                  │
        ADMIT / REJECT / HOLD
                  ▼
       governed Neo4j projection
                  │
      exact + full-text + vector + graph
                  ▼
Hypothesis / Candidate / Evidence Context
                  │
                  ▼
              CONT writer
```

The writer **does not need to know the Graphiti SDK** and MUST NOT query `newsroom-eval-proposal`. The controller MUST wrap admitted, hydrated, provenance-bearing context before it reaches the writer.

So:

> “The writer does not talk to Graphiti” is the correct boundary;
> “The whole writing pipeline never uses governed GraphRAG” is not.

# 2. How Graphiti temporal currency works


| Time | Meaning |
| --- | --- |
| `reference_time` | The time anchor this source episode describes or relies on |
| `created_at` | When Graphiti actually ingested the episode or fact |
| `valid_at` | When this relationship started to hold |
| `invalid_at` | When this relationship stopped holding |
| `expired_at` | When Graphiti learned or processed that it had been replaced |


Graphiti `add_episode()` builds the episode from `reference_time` and uses it to select related previous episodes. The episode’s own `created_at` is execution time; `valid_at` is the supplied `reference_time`. Graphiti also extracts edge `valid_at` / `invalid_at`. When a newer contradictory fact arrives it usually does not delete the old edge; it marks the old edge invalid and keeps history. Upstream also recommends a background queue and sequential per-episode ingest.

Example:

```text
1 Jan: source reports A is the minister
1 Mar: source reports B succeeds A
20 Aug: Newsroom first ingests both documents
```

The correct result is:

```text
A —HOLDS_ROLE→ Ministry
valid_at   = 1 Jan
invalid_at = 1 Mar
created_at = 20 Aug

B —HOLDS_ROLE→ Ministry
valid_at   = 1 Mar
created_at = 20 Aug
```

The system can then answer:

- what sources said in January;
- who is current after March;
- when Newsroom first learned both facts.

Remember that Graphiti’s LLM-extracted `valid_at` / `invalid_at` remain a **PROPOSED temporal interpretation**. A timestamp does not make them facts.

# 3. The worst current defect is not “5 to 1”; it is the wrong time

The current adapter passed adapter start time into Graphiti as `reference_time`: “when this Graphiti run started” instead of “which time the source content is about”.

That causes:

- historical backfill to look as if it happened today;
- old news, new news and revisions ingested on the same day to share one time anchor;
- correction and supersession order to be wrong;
- Graphiti cannot tell source time from knowledge-ingest time;
- later graph lookups of “current” may not be current.

More importantly, one Evidence Package can contain several sources and several dates, yet the whole package was joined into one Graphiti episode sharing one `reference_time`. Replacing `started_at` with a single publication time is not enough — **the ingest unit itself was wrong.**

The repository already retains enough data: `SourceRevisionRequest` keeps `source_published_time`, `source_updated_time` and `observed_at`; `DiscoveryOccurrenceRequest` has `source_asserted_time`. Those times were dropped at the Graphiti evaluation bridge.

The correct approach is:

- each Graphiti episode belongs to one immutable `SourceRevision` / `DiscoveryRepresentation`;
- long documents MAY split into ordered chunks, but one episode MUST NOT mix several source revisions;
- `reference_time` comes from a versioned temporal policy;
- published, updated, asserted, observed, ledger-recorded and ingested times stay distinct;
- missing source time MAY fall back to `observed_at` only when labelled `OBSERVED_FALLBACK`.

# 4. Five remaining gaps on the existing Graphiti path

## 1. Input was the Story Candidate, not the source corpus

The path formed a Candidate, built an Evidence Package, then fed Candidate passages to Graphiti. Attempts were keyed by `story_candidate_id`.

So a source that:

- never formed a Candidate;
- already existed as a duplicate Candidate;
- hit the writer cap;
- was background material rather than a news Candidate;

might never enter the Graphiti corpus in time.

Corpus memory MUST trigger on a rights-permitted new Source Revision, not on “which draft was written today”.

## 2. Identity and idempotency were unstable

`evaluation_attempt_for()` minted new random IDs, and `add_episode()` was not given a stable create-safe identity. graphiti-core 0.29.3 treats `add_episode(uuid=...)` as lookup, not create.

Formal corpus ingest MUST derive deterministic idempotency from:

```text
source identity
+ observation / representation digest
+ source timestamps
+ chunk digest / chunk ordinal
+ Graphiti configuration semantic digest
+ temporal policy digest
```

Newsroom retains that key on the receipt. It MUST NOT pass a never-written UUID into 0.29.3 `add_episode(uuid=)`.

## 3. Graphiti extracted relations; Newsroom did not retain them as proposals

`_proposals_from_result()` only walked `result.nodes` into `ENTITY_MENTION`. Edges MUST become typed relation proposals with passage evidence, not a count.

## 4. Source IDs were treated as world entities

An Evidence Package prefix of internal source IDs in the episode body caused Graphiti to extract `HK-04` or `RAD-02` as world entities.

Those MUST NOT be extracted as world entities. `SourceItem`, `SourceRevision`, `DERIVED_FROM` and `OBSERVED_IN` lineage belongs to the deterministic projector. Graphiti extracts people, organisations, events, policies and relations in the source content.

## 5. “Disposable workspace” lifecycle was ambiguous

Each attempt’s local filesystem scratch is deleted. The Graphiti Neo4j group accumulates episodes across attempts.

Keeping the untrusted graph across episodes is required for corpus linking. The error was failing to separate:

- **Attempt scratch workspace:** cleaned after each execution;
- **Proposal generation:** retained across corpus episodes, without authority, and rotatable, quarantinable or wipeable.

A generation MUST bind framework, model, prompt, embedding, ontology, temporal policy, generation ID and input watermark. Different versions MUST NOT share one fixed group indefinitely.

# 5. How to read 176 payloads versus 3 Graphiti attempts

176 is output payloads; 3 is candidate-keyed successful attempts. True corpus coverage uses unique eligible Source Revisions / Representations as the denominator.

A Graphiti currency dashboard MUST show eligible source revisions, successfully ingested revisions, held / failed / dead-letter revisions, a contiguous input watermark, the oldest unresolved gap, latest source-time covered, oldest and p95 ingest lag, proposal admission backlog, governed projection watermark, and actual and reserved spend.

# 6. Cost and money

£250 is a **cash ceiling / reservation permission**, not £250 already prepaid or spent. The wallet contract uses `GBP_MINOR_UNITS` for ceiling and debit.

Graphiti **chat** no longer uses OpenRouter `gpt-5-mini`. Chat uses cursor-agent CLI `composer-2.5`, then Grok Build CLI `grok-4.6` medium. Both are subscription CLIs, same rule as the CONT writer: **ledger them, do not debit OD-011 £250.**

Embeddings remain metered under OD-011:

```text
text-embedding-3-large US$0.13 / 1M tokens
```

Rough embedding formula:

```text
embedding_tokens × 0.13 / 1,000,000
```

excluding routing, retry, provider adjustment and GBP conversion.

One `add_episode()` is **not** one model call. It can include entity extraction, node dedupe, edge extraction, edge contradiction resolution, timestamp extraction, attribute extraction and embeddings. Chat uses the CLI; embedding calls still use OpenRouter.

Where the provider does not supply usage, the receipt MUST label usage as unreported rather than treat a silent zero as a measured invoice. Formal decoupled ingest still needs:

```text
reserve worst-case amount for metered embeddings
→ execute calls
→ record CLI chat invocations (unmetered subscription)
→ record provider-native embedding usage and USD cost
→ convert under versioned GBP FX policy
→ debit actual embedding amount
→ release unused reservation
→ reconcile against OpenRouter invoice for embeddings
```

Otherwise an ingest queue can drain the backlog and the embedding budget while the ledger only knows “reserved”.

Read strictly with `GRAG-022` and #707 (“every model and embedding call ledgered”), the accounting gap still needs closing. Do not weaken the specification to hide it.

# 7. Graphiti 0.29.3 qualification risk

Upstream still has an open bug report against 0.29.3: edge invalidation candidate search may find semantically similar facts across the whole `group_id`, so unrelated facts that merely share an entity can retire each other.

That does not mean we should not use Graphiti. It does mean:

- currentness / invalidation MUST NOT become authority;
- a shared corpus group needs adversarial false-invalidation tests;
- 0.29.3 needs a patch, a structural guard, disabled automatic invalidation, or a qualified fixed release;
- every invalidation MUST be retained as a proposal / evidence, not disappear.

Upstream also reports that node attributes lack full temporal versioning and newer values can overwrite older ones. Time-varying newsroom facts SHOULD stay as reified relation / assertion versions, not mutable node properties such as “current post”, “location” or “headcount”.

Both points confirm the original product logic: Graphiti is proposal-only; governed admission is separate.

# 8. How the three options are judged


| Option | Judgement | Reason |
| --- | --- | --- |
| 1. Keep 5 writes → 1 Graphiti per cycle | **EVALUATION throttle only** | Scheduling is bound to drafts; it is not corpus coverage and does not help the current draft |
| 2. Decouple corpus ingest | **Slice A, land now** | Build correct source-revision memory, time, coverage and cost control |
| 3. Decouple ingest, then add admitted retrieval | **Final product target (Slice B, still gated)** | Can reduce repetition and add history and correction context before Hypothesis / Candidate / Evidence / draft |


Graphiti upstream itself recommends background sequential episode ingest, so option 2 matches its design rather than violating it.

# 9. Which specification to change

## Core GRAG specification: do not rewrite it

The existing specification already requires proposal-only extraction, separate admission, distinct temporal dimensions, retained extraction cost, hybrid retrieval, provenance hydration, watermark / gap, and that GraphRAG context MUST NOT allocate Candidate authority. The direction is correct.

## `CONT-001`: do not change the core sentence yet

`CONT-001` already says: approved evidence package and permitted structured context. That already reserves a place for safe GraphRAG context.

Slice B adds a narrower contract: permitted structured context MUST be ADMITTED, trust-labelled and provenance-hydrated, and MUST carry projection watermark / gap metadata. PROPOSED Graphiti workspace data MUST NOT reach the writer.

## #707: do not rewrite a completed historical record

#707 is the private beta live proof. Keep it as `writer + Graphiti execute smoke proof`. Do not re-explain it as complete corpus GraphRAG.

This file is the #722 PM decision and the Graphiti SSOT.

# 10. Normative locks (GING)

### GING-001 — Corpus-owned scheduling

Graphiti ingest MUST be driven by rights-permitted `SourceRevision` / `DiscoveryRepresentation` readiness. It MUST NOT be driven by draft count or writer completion. The five-writes-then-one-Graphiti sequence MAY remain an EVALUATION throttle on how many ingest units run per cycle. It MUST NOT be the target corpus schedule.

### GING-002 — Exact ingest identity

Each episode MUST bind one immutable source revision / representation. It MUST NOT mix several source revisions. Episode identity and idempotency MUST be deterministic from source identity, observation or representation digest, source timestamps, chunk digest / ordinal, Graphiti configuration semantic digest and temporal policy digest.

### GING-003 — Versioned temporal mapping

`reference_time` MUST be derived from retained source times by a versioned policy. `started_at` MUST NEVER replace source time. Missing source time MAY fall back to `observed_at` only when labelled `OBSERVED_FALLBACK`. Published, updated, asserted, observed, ledger-recorded and ingested times MUST be retained separately.

### GING-004 — Proposal-generation lifecycle

Graphiti untrusted graph MUST persist across episodes so the corpus can link. It MUST belong to an explicit generation that can rotate, quarantine or wipe. Attempt scratch cleanup MUST NOT imply proposal-generation deletion. A generation MUST bind framework, model, prompt, embedding, ontology, temporal policy, generation ID and input watermark.

### GING-005 — Complete durable proposal receipt

Before admission the system MUST retain entities, relations, source / target identities, fact text, episode and passage provenance, `reference_time`, `valid_at` / `invalid_at`, raw output digest, framework / model / prompt versions, token usage and provider cost. A Neo4j private workspace or `proposal_count=3` is not enough.

### GING-006 — Currency and coverage telemetry

The system MUST expose exact eligible denominator, watermark, gap, lag, retry, dead letter, admission backlog and actual spend. Unpublished payload count MUST NOT stand for graph coverage.

### GING-007 — Governed context boundary

Writer, Hypothesis and Candidate controllers MUST receive only ADMITTED, hydrated context. Graphiti raw nodes, edges, rank and invalidations MUST NOT become publication evidence. During Slice A the CONT writer remains Evidence Package-only.

Internal source IDs such as HK-04 or RAD-02 MUST NOT become world entities or editorial relations merely because they appear in an episode prefix.
