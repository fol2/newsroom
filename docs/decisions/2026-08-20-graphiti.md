# 「Graphiti currency」其實有三層意思

1. **Currently works**：而家實際點運作；
2. **Temporal currency**：Graphiti 點知道一件事而家仍然有效、已過時，或者後來被推翻；
3. **Monetary currency**：實際成本同 £250 budget 點扣。

# 一、Graphiti 喺我哋產品入面到底係乜

Graphiti 唔應該被理解成：

> 幫某一篇稿抽幾個 entity，等下一篇可能用到。

比較準確嘅理解係：

> Graphiti 係一個會逐個讀入 source episodes、跨來源做 entity resolution、抽取 relationships、識別新舊事實同可能矛盾嘅 **temporal proposal engine**。

喺 Newsroom 架構入面，佢仍然只係：

```text
stochastic extractor / proposal producer
```

而唔係：

```text
editorial authority
```

真正 authority 仍然係 relational ledger、retained permitted objects、admission decisions 同 governed projector。Graphiti private graph 可以被清走；已承認嘅 entity／relation history 唔可以依賴佢先存在。呢一點現有 GRAG spec 其實寫得正確：Graphiti proposal-only、workspace isolated、separate admission、graph projection non-authoritative。

理想流程應該係：

```text
SourceRevision / DiscoveryRepresentation
                  │
                  │ rights + access gate
                  ▼
        Graphiti corpus ingest queue
                  │
                  ▼
      untrusted proposal generation
      entities + relations + timestamps
                  │
                  ▼
        retain exact proposal receipts
                  │
        ADMIT / REJECT / HOLD
                  ▼
       governed Neo4j projection
                  │
      exact + full-text + vector + graph
                  ▼
Hypothesis / Candidate / Evidence Context
                  │
                  ▼
              CONT writer
```

Writer **唔需要直接識 Graphiti SDK**，亦唔應該查 `newsroom-eval-proposal`。應該係 controller 將已承認、已 hydrate、帶 provenance 嘅 context 包好，再交俾 writer。

所以：

> 「Writer 唔理 Graphiti」係正確邊界；
> 「整條 writing pipeline 永遠唔理 governed GraphRAG」就唔正確。

# 二、Graphiti 嘅 temporal currency 點運作


| 時間 | 意義 |
| --- | --- |
| `reference_time` | 呢個 source episode 所描述／依據嘅時間錨點 |
| `created_at` | Graphiti 幾時真正 ingest 呢個 episode／fact |
| `valid_at` | 呢段 relationship 由幾時開始有效 |
| `invalid_at` | 呢段 relationship 由幾時開始唔再有效 |
| `expired_at` | Graphiti 幾時得知／處理到佢已被取代 |


Graphiti `add_episode()` 會以 `reference_time` 建立 episode，並用佢揀相關 previous episodes；episode 自己嘅 `created_at` 係執行當下，而 `valid_at` 係 supplied `reference_time`。Graphiti 亦會抽取 edge 嘅 `valid_at`／`invalid_at`，遇到較新而矛盾嘅事實時，通常唔係刪除舊 edge，而係將舊 edge 標成失效，保留歷史。上游亦明確建議用 background queue，並逐個 episode sequentially ingest。

例如：

```text
1 Jan：來源報道 A 是部長
1 Mar：來源報道 B 接替 A
20 Aug：Newsroom 才首次 ingest 兩份文件
```

正確結果應該係：

```text
A —HOLDS_ROLE→ Ministry
valid_at   = 1 Jan
invalid_at = 1 Mar
created_at = 20 Aug

B —HOLDS_ROLE→ Ministry
valid_at   = 1 Mar
created_at = 20 Aug
```

咁系統先可以同時回答：

- 1 月嗰陣來源講緊乜；
- 3 月之後邊個先係 current；
- Newsroom 係幾時先知道呢兩件事。

但要記住，Graphiti 用 LLM 抽出嚟嘅 `valid_at`／`invalid_at` 都只係 **PROPOSED temporal interpretation**，唔會因為佢有 timestamp 就自動變成事實。

# 三、現行實作最嚴重唔係「5 比 1」，而係時間用錯咗

現行 adapter 將執行開始時間傳入 Graphiti 作為 `reference_time`。即係用「Graphiti 今次幾時開始執行」代替「來源內容講緊邊個時間」。

呢個會導致：

- 歷史文件 backfill 全部睇落好似今日先發生；
- 同一日 ingest 嘅舊聞、新聞、修訂可能擁有同一時間錨；
- correction／supersession 嘅先後次序可能錯；
- Graphiti 無法準確分辨 source time 同 knowledge-ingest time；
- writer 將來就算查到 graph，得到嘅「current」亦未必真係 current。

更關鍵係，一個 Evidence Package 可以包含幾個來源、幾個不同日期，但目前成個 package 被 join 成一個 Graphiti episode，全部共用同一個 `reference_time`。所以單純將 `started_at` 改成其中一個 publication time 都唔夠——**ingest unit 本身就錯咗。**

Repo 已經有足夠資料解決：`SourceRevisionRequest` 本身保留 `source_published_time`、`source_updated_time`、`observed_at`；`DiscoveryOccurrenceRequest` 亦有 `source_asserted_time`。只係呢啲時間去到 Graphiti evaluation bridge 時全部掉失咗。

正確做法應該係：

- 每個 Graphiti episode 只屬於一個 immutable `SourceRevision`／`DiscoveryRepresentation`；
- 長文件可以分多個 ordered chunks，但唔可以一個 episode 混合幾個來源修訂；
- `reference_time` 由一個 versioned temporal policy 決定；
- 原本嘅 published、updated、asserted、observed、ledger-recorded、ingested time 全部獨立保留；
- 缺少來源時間時可以 fallback 到 `observed_at`，但必須標示 `OBSERVED_FALLBACK`，唔可以靜靜當作來源時間。

# 四、現有 Graphiti path 仲有五個實質缺口

## 1. Input 係 Story Candidate，而唔係 source corpus

而家係先形成 Candidate，再做 Evidence Package，再用 Candidate passages 餵 Graphiti。Graphiti attempt 亦以 `story_candidate_id` 去記錄。

所以一份來源如果：

- 冇形成 Candidate；
- Candidate 已經重複；
- Writer cap 已滿；
- 來源屬背景資料而未成新聞；

佢就未必會及時進入 Graphiti corpus。

但 corpus memory 應該由「有一個 rights-permitted 新 Source Revision」觸發，而唔係由「今日啱啱寫咗邊篇稿」觸發。

## 2. Identity 同 idempotency 唔穩定

`evaluation_attempt_for()` 每次建立新嘅 random IDs，而呼叫 `add_episode()` 時亦冇傳 stable `uuid`。

正式 corpus ingest 應該由以下內容推導 deterministic idempotency：

```text
source_revision_id
+ representation_digest
+ chunk_digest / chunk ordinal
+ Graphiti configuration semantic digest
+ temporal policy digest
```

## 3. Graphiti 抽到 relations，但 Newsroom 冇保留

`_proposals_from_result()` 只遍歷 `result.nodes` 變成 `ENTITY_MENTION`。`result.edges` 只用來計 `relation_count`，冇轉做 relation proposals；private JSON graph 嘅 `relations` 更加直接係空 tuple。

即係目前嚴格嚟講只係 Graphiti entity-extraction smoke proof，加一個未受治理嘅 temporary relation graph。仲未係 spec 所描述嘅 governed relation proposal pipeline。

## 4. Source IDs 被當成世界實體

Evidence Package 將內部 source ID 當普通文字 prefix 放入 episode body，令 Graphiti 抽出 `HK-04`、`RAD-02` 呢類 registry 代號當 world entities。

呢啲唔應該由 LLM 當 world entities 抽出。`SourceItem`、`SourceRevision`、`DERIVED_FROM`、`OBSERVED_IN` 呢類 lineage 應該由 deterministic projector 建立；Graphiti 應該抽新聞內容入面嘅人物、組織、事件、政策同關係。

## 5. 「Disposable workspace」生命周期含糊

每次 attempt 嘅 local filesystem scratch workspace 確實會被刪除。但真正 Graphiti Neo4j group 會跨 attempts 繼續累積 episodes。

跨 episode 保留其實係 corpus linking 所需要，唔係錯；錯在未清楚分開：

- **Attempt scratch workspace**：每次執行後清理；
- **Proposal generation**：跨 corpus episodes 保留，但無 authority，可以明確 rotate／quarantine／wipe。

Proposal generation 仲應該綁定 framework、model、prompt、embedding、ontology、temporal policy、generation ID 同 input watermark。唔應該將不同版本長期混入同一個固定 group。

真正「Graphiti currency dashboard」應該顯示 eligible source revisions、successfully ingested revisions、held／failed／dead-letter revisions、contiguous input watermark、oldest unresolved gap、latest source-time covered、oldest and p95 ingest lag、proposal admission backlog、governed projection watermark、actual and reserved spend。

# 六、費用／貨幣方面而家點運作

`£250` 目前係一個 **cash ceiling／reservation permission**，唔係已經預付或已花 £250。Repo 嘅 wallet contract 亦用 `GBP_MINOR_UNITS` 表達 ceiling 同 debit。

Graphiti **chat** 而家唔再行 OpenRouter `gpt-5-mini`。Chat 用 cursor-agent CLI `composer-2.5`，失敗則 Grok Build CLI `grok-4.6` medium。呢兩條都係 subscription CLI，同 CONT writer 一樣：**要入 ledger，但唔從 OD-011 £250 debit。**

仍然計量、仍然受 OD-011 約束嘅係 embeddings：

```text
text-embedding-3-large US$0.13 / 1M tokens
```

粗略 embedding 計算式：

```text
embedding_tokens × 0.13 / 1,000,000
```

未計 routing、retry、provider adjustment 同 GBP conversion。

一個 `add_episode()` **唔等於一個 model call**。佢可以涉及 entity extraction、node dedupe、edge extraction、edge contradiction resolution、timestamp extraction、attribute extraction 同 embeddings。Chat 呼叫行 CLI；embedding 呼叫仍然行 OpenRouter。

Adapter 而家將 token／cost 寫成 0。正式 decoupled ingest 前，應該先有：

```text
reserve worst-case amount for metered embeddings
→ execute calls
→ record CLI chat invocations (unmetered subscription)
→ record provider-native embedding usage and USD cost
→ convert under versioned GBP FX policy
→ debit actual embedding amount
→ release unused reservation
→ reconcile against OpenRouter invoice for embeddings
```

否則一拆開 ingest queue，佢可能快速清 backlog，同時快速消耗 embedding budget，但 ledger 仍然只知道「reserved」。

嚴格按 `GRAG-022` 同 #707「every model and embedding call ledgered」去理解，accounting gap 仍然要補，唔應該靠改弱 spec 去掩蓋。

上游有一個仍然 open、以 0.29.3 code 為基礎嘅 bug report：edge invalidation candidate search 可能喺成個 `group_id` 入面搵語意相似 facts，令只係共享一個 entity、但實際無關嘅事實互相 retire。

呢個唔代表我哋唔應該用 Graphiti，但代表：

- currentness／invalidation 絕對唔可以直接成為 authority；
- shared corpus group 要做 adversarial false-invalidation test；
- 0.29.3 要 patch、加 structural guard、disable automatic invalidation，或者升級到經資格驗證嘅 fixed version；
- 所有 invalidation 都應該被保留為 proposal／evidence，而唔係直接消失。

上游亦有 open issue 指出 node attributes 缺乏完整 temporal versioning、較新值可以覆蓋舊值。因此會隨時間變化嘅 newsroom facts，應該繼續用 reified relation／assertion versions 表達，而唔係將「現任職位」「所在地」「人數」直接當可變 node properties。

呢兩點反而證明我哋原本「Graphiti proposal-only、governed admission separate」嘅產品邏輯係正確。

| 選項 | 判斷 | 原因 |

| 1. 維持每 cycle 5 writes → 1 Graphiti | **只保留作短期 EVALUATION throttle** | 排程同稿件綁死，唔代表 corpus coverage；亦幫唔到當前 draft |

# 十、Normative locks（GING）

### GING-001 — Corpus-owned scheduling

Graphiti ingest MUST be driven by rights-permitted `SourceRevision`／`DiscoveryRepresentation` readiness. It MUST NOT be driven by draft count or writer completion. The five-writes-then-one-Graphiti sequence MAY remain an EVALUATION throttle on how many ingest units run per cycle. It MUST NOT be the target corpus schedule.

### GING-002 — Exact ingest identity

Each episode MUST bind one immutable source revision／representation. It MUST NOT mix several source revisions. Episode UUID and idempotency MUST be deterministic from source identity, representation digest, chunk digest／ordinal, Graphiti configuration semantic digest and temporal policy digest.

### GING-003 — Versioned temporal mapping

`reference_time` MUST be derived from retained source times by a versioned policy. `started_at` MUST NEVER replace source time. Missing source time MAY fall back to `observed_at` only when labelled `OBSERVED_FALLBACK`. Published, updated, asserted, observed, ledger-recorded and ingested times MUST be retained separately.

### GING-004 — Proposal-generation lifecycle

Graphiti untrusted graph MUST persist across episodes so the corpus can link. It MUST belong to an explicit generation that can rotate, quarantine or wipe. Attempt scratch cleanup MUST NOT imply proposal-generation deletion. A generation MUST bind framework, model, prompt, embedding, ontology, temporal policy, generation ID and input watermark.

### GING-005 — Complete durable proposal receipt

Before admission the system MUST retain entities, relations, source／target identities, fact text, episode and passage provenance, `reference_time`, `valid_at`／`invalid_at`, raw output digest, framework／model／prompt versions, token usage and provider cost. A Neo4j private workspace or `proposal_count=3` is not enough.

### GING-006 — Currency and coverage telemetry

The system MUST expose exact eligible denominator, watermark, gap, lag, retry, dead letter, admission backlog and actual spend. Unpublished payload count MUST NOT stand for graph coverage.

### GING-007 — Governed context boundary

Writer, Hypothesis and Candidate controllers MUST receive only ADMITTED, hydrated context. Graphiti raw nodes, edges, rank and invalidations MUST NOT become publication evidence. During Slice A the CONT writer remains Evidence Package-only.

Internal source IDs such as HK-04 or RAD-02 MUST NOT become world entities or editorial relations merely because they appear in an episode prefix.

# PM decision recorded on #722

```text
Decision: Option 3 is the target architecture, delivered in two gated slices.

Slice A decouples Graphiti corpus ingest from CONT writing. Ingest is driven by
rights-permitted SourceRevision / DiscoveryRepresentation readiness, uses exact
immutable source identity and a versioned temporal mapping, and retains complete
entity, relation, provenance, usage and cost proposals before admission. CONT
remains Evidence Package-only during this slice. Graphiti chat uses cursor-agent
CLI composer-2.5, then Grok Build CLI grok-4.6 medium. Embeddings remain
OpenRouter text-embedding-3-large under OD-011.

Slice B introduces governed retrieval into Hypothesis consolidation, Candidate
formation, Evidence assembly and drafting. Only ADMITTED, provenance-hydrated,
trust-labelled context with projection watermark and gap metadata may be supplied.
Raw PROPOSED Graphiti workspace state must never enter the writer or publication
evidence.

The existing five-writes-then-one-Graphiti sequence remains an EVALUATION throttle
only and is not the target corpus schedule.
```

最核心嘅判斷係：

> **產品 spec 唔係錯；而家 beta implementation 只證明 Graphiti 跑得到，未證明佢已經用正確 source identity、source time、relation retention、coverage 同 cost accounting 織緊整個來源庫。**

所以應該做嘅係 **加窄而精確嘅 amendment，同埋修正 implementation**，唔係將原本正確嘅 GraphRAG／authority spec 改弱去遷就現有 cycle。
